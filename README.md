# Bai Blind Box

The player site, bilingual rules, and Solidity source for Bai Blind Box. The current test deployment is BSC Testnet v10 (Chain ID 97), recorded in [`deployments/bsc-testnet-v10.json`](deployments/bsc-testnet-v10.json); v8 and v9 deployment records remain available for audit.

The game price is 10 USDT per box. A qualifying direct inviter earns 3 USDT for each box purchased by their referred wallet. The inviter must have previously purchased a box. For direct-USDT payments, the buyer signs one short-lived, one-time message only when requesting a deposit address; it binds the site origin, chain, buyer, and inviter. This message signature costs no gas and grants no token allowance. Wallet connection, collection browsing, and public reads do not require a signature. The API then returns a deterministic vault bound to the buyer and inviter; no setup transaction is required. The Keeper cannot reassign a funded buyer vault to another wallet. Each buyer can bind one inviter, and the binding cannot be changed. There is one referral level. Free claims, card trades, and synthesis do not earn commission. The 3 USDT commission is deducted from the 7.8 USDT liquidity allocation for that referred box; the 2.2 USDT prize allocation is unchanged. Without a referral, the full 7.8 USDT goes to liquidity. Direct-USDT transfers are indexed and settled by the backend Keeper; a registered order that remains unsettled can be refunded after 24 hours from registration.

Synthesis requires four revealed losing cards. For a paid-box card, its BAI reward must be claimed before the card can be used as synthesis material; this releases its reserved reward liability before the NFT can be burned. Synthesized cards have no paid-box BAI reward. Synthesis requests are globally limited to 50 per Beijing day because synthesis and daily draws share the Chainlink VRF subscription. The keeper waits for the on-chain sales cutoff before requesting paid-round randomness and emits an alert when the free-reward FIFO is blocked by an unfulfilled day.

Free claims award BAI only. Each wallet can register once per Beijing day; the campaign is capped at 3,000 entries per day and 200,000 total. The reserve covers 195,000 standard rewards of 1–3 BAI and 5,000 special rewards of 4–6 BAI. Chainlink VRF assigns rewards after the claim day closes. If a request remains unfulfilled for 24 hours, only the deployer or configured purchase Keeper may submit a replacement request; this prevents public callers from repeatedly consuming subscription funds. Unclaimed rewards remain pending until the wallet has purchased a paid box. The v10 game and free-reward contract are registered as consumers on the testnet VRF subscription.

The testnet liquidity manager uses a 15-second TWAP, 5-second observation interval, and 2 USDT pool floor. Its initial LP shares are locked. These are testnet settings; mainnet uses a separate deployment configuration. `marketReady` is transient: the Keeper must keep posting fresh observations (no older than 300 seconds), or paid purchases pause automatically. The v10 deployment was ready after initial warmup, but the latest live read is paused because no persistent Keeper has been running.

## Build and deploy

NFT metadata is generated on-chain by `BAICardMetadataRenderer`: sealed boxes expose a pending state, and revealed cards expose their asset, rarity, style, result, Beijing day, and embedded SVG image. Four card skins are represented as distinct metadata traits.

Install dependencies with `npm ci`, compile with `npm run compile`, and run the local contract sandbox with `npm run sandbox:simulate`. The deployed testnet currently uses an older contract version; direct USDT transfers require a fresh v12 deployment. For that deployment, copy `.env.testnet.example` to `.env.testnet`, configure the deployer, a purchase Keeper address that matches the backend Keeper key, treasury, VRF subscription, and a public HTTPS `PUBLIC_API_BASE_URL`. Run `npm run deploy:testnet:check` before `npm run deploy:testnet`; the read-only preflight checks configuration and chain prerequisites. The API cannot pass `/readyz` until the new contract addresses exist, so API readiness is checked after deployment. Deployment seeds the first TWAP observation and exits without waiting for the market to warm up. Start the Keeper so it continues recording observations (the oracle enforces a minimum 5-second spacing; the Keeper's default loop is 15 seconds). The testnet TWAP window is 15 seconds, so rerun the readiness check after at least 15 seconds from the initial observation. Keep the Keeper running afterward: observations older than 300 seconds make paid purchases pause automatically. If the v12 script records `DEPLOYED_BACKEND_PENDING`, configure and start the API, indexer, and Keeper from the generated manifest, then rerun `npm run deploy:testnet` to complete readiness without redeploying the recorded contracts. Finally run `BSC_TESTNET_RPC_TRANSPORT=curl BAI_TESTNET_MANIFEST=bsc-testnet-v12.json npm run verify:testnet`. The verifier checks buyer-specific vault derivation, processor wiring, USDT token code, frontend/API addresses, VRF consumers, reserves, and market readiness. Direct-USDT address requests use `POST /v1/deposit-challenge` and a five-minute, one-use wallet message signature, then `POST /v1/deposit-address`; only verified vaults are added to the indexer registry. Card faces use recognizable vector marks for their represented assets; the marks are included directly in the card art and on-chain NFT metadata.

The wallet button supports standard Binance Web3 Wallet providers and desktop WalletConnect QR pairing. This is not Binance Agentic Wallet authentication and cannot verify Agentic Wallet identity. Binance explicitly warns users not to scan third-party site QR codes to sign in to Agentic Wallet because that can give the site control of the wallet; use only the approved Agentic Wallet AI agents/skills for that product ([Binance security FAQ](https://www.binance.com/en/support/faq/detail/3ff00e2d488a41c4aaa4aabb6fc36763)). QR pairing uses WalletConnect Universal Provider; `WALLETCONNECT_PROJECT_ID` is a public project identifier obtained from WalletConnect Cloud. Set it in `.env.testnet` or `.env.mainnet` before deployment so the generated public config can render the QR, and allowlist the deployed HTTPS origin in the WalletConnect dashboard. A pairing approval only establishes a standard wallet session and exposes its address; it does not sign a message or send a transaction. Every on-chain action still opens a separate wallet confirmation.

See [`README-mainnet-deploy.md`](README-mainnet-deploy.md) for the separate mainnet deployment checklist. Never put private keys or seed phrases in this repository.

The mainnet preflight also requires `VRF_MIN_NATIVE_BALANCE_BNB`; this is an operator-set minimum reserve, not a guarantee that the subscription can fund every request. Set it using the expected daily draw and synthesis request volume and monitor/top up the subscription. The free-reward campaign preserves exact global standard/special quotas with FIFO settlement, so a prolonged VRF outage on an earlier day can still pause later free-reward settlements.

To inspect the currently recorded testnet deployment against live read-only chain state, run `BSC_TESTNET_RPC_TRANSPORT=curl npm run audit:testnet`. It chooses the v12 manifest when present, otherwise falls back to v10, and reports contract code, frontend alignment, oracle/TWAP readiness, VRF balances and consumers, and reward-reserve coverage. `NOT_READY` exits nonzero; this audit never submits transactions. `npm run verify:testnet` remains the stricter v12 deployment verifier.
